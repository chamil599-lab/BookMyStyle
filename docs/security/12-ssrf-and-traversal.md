# 12 - SSRF and path traversal

Checked 16 October 2026. No exploitable server-side request forgery or request-controlled filesystem traversal was found in the reviewed paths. No production code changes were needed.

Reviewed authored HTTP/network calls, URL ingestion, file reads/writes/deletes, filesystem configuration, image accessors and API uploads, Spatie upload persistence and Laravel private-file serving. Image src_url fields are stored and rendered for browser loading; the reviewed application does not download them, proxy them or pass them into addMediaFromUrl. Google verification uses the official client's fixed Google certificate endpoint, not a caller-selected URL. Deployment manifest/file scans use deployment-controlled roots and are not request file-read endpoints. No request-derived include/require, shell execution or XML parser sink was found in app/routes.

Upload directories/disks are selected by server code. API image uploads ignore forged upload_path/directory/disk fields and generate a path within the public image_cycles directory. Installed Spatie upload code reads the temporary uploaded file content and associates it with the authorized record; salon deletion callbacks select media from that record's collection. Laravel ServeFile requires a relative signature for private disks and catches Flysystem PathTraversalDetected. The configured local disk root is private storage; public media has a separate root.

Added ten cases: four forbidden source URL schemes; external URL metadata persistence without a Laravel Http-client request or stored file; forged upload destination fields; unsigned private download denial; and three traversal variants at the installed storage-serving boundary. Combined with UploadSecurityTest: **20 tests passed, 77 assertions**. Fixtures are synthetic and storage disks are fake; no private address, metadata service or real secret file was contacted/read. Imported MySQL data was untouched.

Limits: Http::assertNothingSent monitors Laravel's HTTP facade, not every possible networking library. The no-fetch conclusion also relies on source tracing; this was not packet capture, DNS-rebinding testing or production network-policy verification. Tests invoke the installed storage handler for traversal/signature checks and do not certify the deployed web server's path decoding, aliases or symlinks. HTTP(S) image URLs may still cause a visitor's browser to make external requests; that differs from server-side fetching. Any future remote-image import, webhook or URL-preview feature needs explicit destination and redirect controls before release.

Reference: [OWASP SSRF prevention guidance](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html). Next category: API security.
