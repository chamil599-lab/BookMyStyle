# 15 - Data exposure

Checked 16 October 2026. No unintended customer-identity or credential exposure was found in the reviewed public responses. No production application changes were needed.

Reviewed public salon/service/editorial payloads, appointment availability, ratings, customer identity/booking responses, private cache headers, production error rendering and release-file scanning. Public salons use a defined projection rather than serializing owner accounts; intentionally public business contact/owner-name fields remain visible. Service prices are omitted when show_price is disabled. Public availability returns time/service/duration/status without customer name/email/phone/user ID or booking record ID. SalonRating hides reviewer email. Editorial endpoints select public content fields. Private customer records remain actor-scoped; identity payloads exclude passwords and remember credentials. Authentication responses use private/no-store headers.

Added four regression tests: exact public availability fields without customer identifiers, reviewer email/owner account-field omission, hidden-price suppression, and a synthetic internal error whose details/trace/file/exception fields remain absent when app.debug is false. Existing tests cover private booking scopes, guest email claims, review publication, unauthorized identity responses and release-readiness configuration.

Validation: **39 tests passed, 157 assertions; one test skipped**, across ApiAccessTest, AuthResponsePrivacyTest, PublicReleaseFilesTest and DeploymentReadinessTest. The skipped test requires symlink creation privileges unavailable on this Windows environment. A separate read-only scan of this checkout's actual public tree passed all five checks: tree inspection, absence of known repository metadata and backup/key artifacts, front-controller-only scripts, and reviewed public symlink targets. Scan output contained statuses only, not filenames or file contents. Synthetic SQLite fixtures only; imported MySQL data was untouched.

Limits: production must disable debug and use the public directory as document root. The test explicitly sets debug off; it does not certify deployed settings. The local file scan is based on known filenames/extensions and metadata, not exhaustive secret-content detection or live HTTP probes. Aggregate booking/client counts, appointment time/service information, public business contacts and public media remain intentionally accessible. Review text/content can itself contain information entered by users. Logs, backups, hosting permissions, retention and externally served assets need operational review; this result does not certify them.

Reference: [OWASP REST security guidance](https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html). Next category: browser security headers and CSP.
