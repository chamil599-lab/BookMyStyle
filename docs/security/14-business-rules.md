# 14 - Business-rule security

Checked 16 October 2026. Reviewed booking/subscription workflows passed locally. No production code changes were needed.

Reviewed public and management booking creation/updates, capacity calculations, service ownership/publication, slot alignment/opening hours, quota enforcement, cancellation and stale-record handling. Public status/account association are derived server-side. Pending/approved appointments consume peak concurrent capacity; rejected/completed history does not. Service duration is rounded up to 30-minute slots. Shared writes lock owner/salon/booking records, reauthorize and reject stale booking edits. Owner quotas are checked in shared services; administrators intentionally have broader management permissions. Existing tests exercise adjacent slots, long overlapping services, full capacity, past/out-of-hours appointments, zero/monthly quotas, completed-booking reopening and rollback notification behavior.

Reviewed subscription requests, approval, cancellation, payment edits, trials and expiry. Client-supplied amounts/status/dates do not activate requests. Approval requires an authorized administrator and a pending record; payment details can change only while pending. Existing paid access remains intact while another request is pending. Same-plan renewals begin after the latest existing period; a different approved plan starts immediately and cancels the previous active records. Future periods do not grant early access. Duration comes from the request snapshot. Trial granting refuses owners with any subscription history. Tests cover these previously agreed behaviors.

Added four cases: duplicate pending requests cannot extend paid access; cancelled requests cannot be approved or have payment details edited; a stale owner booking edit cannot undo a newer customer cancellation; and unpublished public services cannot consume capacity. **73 tests passed, 670 assertions**, across SharedServicesTest, LegacyRouteRetirementTest and FilamentManagementTest. Synthetic SQLite fixtures only; imported MySQL data was untouched.

Limits: SQLite sequential tests do not prove MySQL row-lock behavior under concurrent processes. Source review found transactions and stable owner/salon lock ordering, but real concurrent booking/quota/approval testing still requires an isolated MySQL rehearsal. Payments are manually approved requests; selecting OnePay does not prove a completed provider payment. An authorized administrator may approve an amount different from the package price, including zero, so payment verification remains an administrative responsibility. Bank-reference reuse and guest booking/contact ownership are not payment-provider or identity verification mechanisms. Anonymous booking abuse remains subject to application rate limits, not a guarantee against distributed slot hoarding. No real payment, email or deployment action was performed.

Reference: [OWASP business logic guidance](https://cheatsheetseries.owasp.org/cheatsheets/Business_Logic_Security_Cheat_Sheet.html). Next category: data exposure.
