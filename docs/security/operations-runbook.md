# Monitoring and recovery before production

This is an implementation/verification runbook, not evidence that any hosting service is configured. Assign a responsible operator and escalation contact before launch. Keep provider destinations, credentials and backup manifests private.

1. Configure log rotation and access. Use the existing daily channel (for example LOG_STACK=daily with an agreed LOG_DAILY_DAYS retention), or a reviewed centralized collector. The source default stack uses single-file logging, which requires host rotation. Restrict storage/logs and failed-job storage; do not expose them through a web alias. Review transport/exception logs for personal information and credential leakage. Do not log Authorization headers, cookies, passwords, reset/Google tokens, raw request bodies or full notification payloads. Protect and rotate access logs too; query strings can contain reset tokens/email addresses.
2. Configure alerts to an explicitly approved operator destination. Monitor availability, application 5xx spikes, repeated 401/403/429 responses, disk capacity, certificate expiry, failed jobs, mail failures, scheduler heartbeat and backup age/failure. Alert delivery and escalation must be tested with synthetic events. /up proves application boot, not database, queue, mail, payment or backup health. A separate reviewed check is needed for dependencies.
3. Implement a durable security audit trail for role/approval changes, subscription approvals/cancellations and account deletion, with actor/target identifiers, event/time/outcome and access controls. Current ordinary application logs are not a complete or tamper-resistant administrative history. Avoid retaining raw customer/payment data as audit context.
4. Review config/operations.php and routes/console.php before cron setup. Both maintenance feature flags default off. Validate dry runs in isolation, the shared cache/lock backend, timezone Asia/Colombo and mail delivery before enabling reminder sending or featured cleanup. Monitor command exit failures and scheduler heartbeats. Reminder cache markers reduce duplicate sends; cache loss or a crash after delivery but before marker persistence can still cause duplicates.
5. If using asynchronous queues, supervise workers, monitor failed_jobs and backlog, and restart workers with releases. Verify retry/timeout settings against job duration. Reconcile externally delivered mail/payments before replaying failed jobs; retrying every failure blindly can repeat external side effects. If notifications run synchronously, monitor request latency/failures instead of assuming workers handle them.
6. Agree recovery-point and recovery-time targets and a backup schedule. Capture matching MySQL data, uploads, release source/lockfiles/assets and private environment/APP_KEY. Encrypt backups, maintain a separate off-site copy, restrict credentials, rotate retention and monitor failed/stale backups. A successful dump or checksum does not prove restorability.
7. Perform the isolated restore in [the rollback guide](../migration/rollback.md). Use a new disposable database/storage target, disable outbound notifications/payments, verify integrity and representative account/booking/subscription/media behavior, and record the private evidence and elapsed recovery time. Never restore over imported/production data to rehearse. The workspace baseline is not an automated production backup.
8. Rehearse release rollback. Pause writes/workers if needed, select the matching verified code/assets/environment, preserve APP_KEY and reconcile bookings/payments created since the backup before any database replacement. Reopen only after smoke checks and monitoring are healthy. Keep failed-release evidence private for investigation.

No alerts, emails, cron entries, backup captures/restores or production configuration changes were performed during this audit.
